Field guide

1. Give it a repeatable failure

Choose a trusted local repository and a linear range: one commit where your check passes, a later one where it fails. Use the same command at every revision.

2. Make the check specific

A dependency-free regression script is ideal. Exit 0 for working, 1–124 for the target failure, and 125 if a revision cannot be tested. Historical dependencies are not installed automatically.

3. Follow the trace

Endpoint checks run first. Git bisect chooses revisions; repeated results are recorded. Inconsistent checks and ambiguous skipped commits stop a precise verdict.

4. Read the evidence

The result confirms a measured boundary under a monotonic good-to-bad assumption. It does not prove why the code is wrong. Use the local AI autopsy for hypotheses, then verify them.

What is supported?

Linear Git histories up to 500 commits, one check at a time, Node 22+ and Git. Committed files only. Existing node_modules and ignored configuration are not copied. Disposable clones isolate Git state, not code execution. Use a trustable, self-contained check.
